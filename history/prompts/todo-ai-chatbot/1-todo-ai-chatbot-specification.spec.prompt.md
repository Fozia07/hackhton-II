# Todo AI Chatbot - Phase III Specification

- **Complete Isolation**: Phase III must be completely isolated from Phase II - no modifications to Phase II code, files, or structures
- **READ-ONLY Phase II**: Phase II frontend & backend folders are strictly read-only - no modifications, overwrites, refactors, or direct imports allowed
- **Separation of Concerns**: Phase III operates in separate top-level folders within the same monorepo
- **No Manual Coding**: All code must be generated by Claude Code based on specs, plans, and tasks

**Isolation Enforcement**: This structure enforces isolation by:
- Using a completely separate directory hierarchy (phaseIII/)
- Having dedicated backend and frontend folders that don't touch Phase II
- Separating concerns with distinct models, components, and configurations
- Maintaining independent dependency management
- Allowing independent deployment and scaling

### 2. Responsibility Boundaries

**What Phase II Provides:**
- Existing DB schema/migrations for Task model (for reference only)
- Neon DB connection details and credentials (shared access)
- Authentication system (JWT tokens, user management)
- Base infrastructure patterns and configurations

**What Phase III MUST NOT Do:**
- Modify Phase II routes, models, or frontend components
- Directly import or reference Phase II code/files
- Change Phase II database tables or schemas
- Override Phase II authentication mechanisms
- Modify Phase II environment variables or configurations

**Database Connection Strategy:**
- Phase III connects to the same Neon PostgreSQL database
- Uses separate tables: Conversation, Message, AgentInteraction
- Maintains user_id scoping for data isolation
- Extends Task table only via new columns if absolutely necessary (prefer new tables)
- Implements proper database transactions and connection pooling

### 3. Agents Architecture

**Main Agent (Todo AI Orchestrator):**
- Purpose: Overall conversation reasoning and tool selection
- Responsibilities:
  - Understands user intents in natural language
  - Selects appropriate MCP tools based on context
  - Manages conversation flow and state
  - Handles error recovery and fallbacks
- Triggers: New user messages, tool execution results, conversation timeouts
- MCP Tool Usage: Coordinates all 5 MCP tools based on user requests

**Sub-Agent (Confirmation Generator):**
- Purpose: Generates appropriate confirmation messages for user actions
- Responsibilities:
  - Creates confirmation prompts for destructive operations
  - Validates user intentions before executing actions
  - Provides feedback on completed operations
- Triggers: Task deletion, task completion, task updates

**Sub-Agent (Error Handler):**
- Purpose: Manages error conditions and provides user-friendly responses
- Responsibilities:
  - Intercepts and categorizes errors
  - Generates appropriate error messages
  - Suggests alternative actions when possible
- Triggers: Tool execution failures, database errors, invalid inputs

### 4. MCP Skills/Tools Specification

**add_task:**
- **Purpose**: Create a new task for the authenticated user
- **Input Parameters**:
  - `title` (string, required): The task title/description
  - `priority` (string, optional): Priority level (low, medium, high)
  - `due_date` (string, optional): Due date in ISO format
  - `category` (string, optional): Task category
- **Output Format**:
```json
{
  "success": true,
  "task": {
    "id": "uuid",
    "title": "string",
    "priority": "string",
    "due_date": "string",
    "category": "string",
    "completed": false,
    "created_at": "timestamp",
    "updated_at": "timestamp"
  }
}
```
- **DB Operations**: INSERT into tasks table with user_id scope

**list_tasks:**
- **Purpose**: Retrieve all tasks for the authenticated user
- **Input Parameters**:
  - `status` (string, optional): Filter by status (all, pending, completed)
  - `category` (string, optional): Filter by category
  - `priority` (string, optional): Filter by priority
- **Output Format**:
```json
{
  "success": true,
  "tasks": [
    {
      "id": "uuid",
      "title": "string",
      "priority": "string",
      "due_date": "string",
      "category": "string",
      "completed": false,
      "created_at": "timestamp",
      "updated_at": "timestamp"
    }
  ]
}
```
- **DB Operations**: SELECT from tasks table with user_id filter

**complete_task:**
- **Purpose**: Mark a task as completed
- **Input Parameters**:
  - `task_id` (string, required): The ID of the task to complete
- **Output Format**:
```json
{
  "success": true,
  "task": {
    "id": "uuid",
    "title": "string",
    "completed": true,
    "completed_at": "timestamp"
  }
}
```
- **DB Operations**: UPDATE tasks table SET completed=true WHERE id=? AND user_id=?

**delete_task:**
- **Purpose**: Remove a task from the user's list
- **Input Parameters**:
  - `task_id` (string, required): The ID of the task to delete
- **Output Format**:
```json
{
  "success": true,
  "deleted_task_id": "string"
}
```
- **DB Operations**: DELETE FROM tasks table WHERE id=? AND user_id=?

**update_task:**
- **Purpose**: Modify an existing task
- **Input Parameters**:
  - `task_id` (string, required): The ID of the task to update
  - `title` (string, optional): New task title
  - `priority` (string, optional): New priority level
  - `due_date` (string, optional): New due date
  - `category` (string, optional): New category
  - `completed` (boolean, optional): New completion status
- **Output Format**:
```json
{
  "success": true,
  "task": {
    "id": "uuid",
    "title": "string",
    "priority": "string",
    "due_date": "string",
    "category": "string",
    "completed": false,
    "updated_at": "timestamp"
  }
}
```
- **DB Operations**: UPDATE tasks table with specified fields WHERE id=? AND user_id=?

**All tools are stateless and user_id-scoped to ensure proper isolation.**

### 5. Phase II Modification Prevention Rules

**File/Directory Protection Rules:**
- Phase II backend (phaseII/backend/) and frontend (phaseII/frontend/) directories are read-only
- No symbolic links or imports to Phase II code
- Separate build and deployment pipelines

**Import Restrictions:**
- No direct imports from Phase II modules/packages
- No referencing Phase II internal functions or classes
- Independent dependency trees (no shared packages that could cause conflicts)

**Database Interaction Rules:**
- Only create new tables in Phase III (Conversation, Message, AgentInteraction)
- Extend Task table only with explicit approval (prefer new tables)
- Always use user_id scoping for data access
- No direct access to Phase II-specific tables or columns
- Use separate database connection pools if possible

**Git Practices:**
- Separate feature branch (001-todo-ai-chatbot) for all Phase III work
- No merging Phase III changes into Phase II branches
- Independent commit history and changelog
- Separate pull request workflows

**Shared Resources Handling:**
- Share .env file but with Phase III-specific variables
- Use same Neon DB URL but with separate table access
- Coordinate with Phase II team for shared resources like authentication tokens
- Maintain separate monitoring and logging systems
