# Todo AI Chatbot - MCP Tools Specification (Step 2)

## 1. Constitution Reinforcement

**Core Isolation Principles:**
- **Complete Isolation**: Phase III must remain completely isolated from Phase II - no modifications to Phase II code, files, or structures
- **READ-ONLY Phase II**: Phase II frontend & backend folders are strictly read-only - no modifications, overwrites, refactors, or direct imports allowed
- **Separation of Concerns**: Phase III operates in separate top-level folders within the same monorepo
- **No Manual Coding**: All code must be generated by Claude Code based on specs, plans, and tasks

**Step 2-Specific Rules:**
- **Pure Functions**: MCP tools MUST be pure functions (no side effects outside DB) - they accept input, perform database operations, and return results
- **No Server Code**: No direct FastAPI/MCP SDK imports or server code yet - this spec is for the tool logic only
- **Exact Format Compliance**: Tools MUST match EXACT input/output formats from requirements (JSON examples) - no deviations
- **Database Scoping**: All DB access via SQLModel session, scoped to user_id for multi-tenancy
- **Stateless Operations**: Tools maintain no internal state - all state persisted in database
- **Error Consistency**: All errors handled consistently with standardized error responses

## 2. MCP Tools Specification

### Tool 1: add_task

**Purpose**: Create a new task for the authenticated user in the database.

**Input Parameters**:
- `user_id` (string, required): The ID of the user creating the task (for scoping and validation)
  - Type: string
  - Required: Yes
  - Validation: Must be a valid user ID that exists in the system
  - Format: Alphanumeric string with possible special characters
- `title` (string, required): The title/description of the task to be created
  - Type: string
  - Required: Yes
  - Validation: Must be between 1-255 characters, not empty or whitespace only
  - Format: Text string
- `description` (string, optional): Additional details about the task
  - Type: string
  - Required: No
  - Validation: If provided, must be between 1-1000 characters
  - Format: Text string, can be null/empty

**Output Format**:
```json
{
  "task_id": "string",
  "status": "created",
  "title": "string"
}
```

**Behavior / Logic**:
1. Validate input parameters: user_id exists and is valid, title is provided and meets length requirements
2. Create a new Task object using SQLModel with provided parameters
3. Assign the provided user_id to scope the task to the correct user
4. Set default values: completed=false, created_at=current_timestamp, updated_at=current_timestamp
5. Insert the new task into the database using SQLModel session
6. Return success response with the generated task ID, status, and title

**SQLModel Syntax Example**:
```python
# Pseudo-code for SQLModel operations
new_task = Task(
    user_id=user_id,
    title=title,
    description=description,
    completed=False,
    created_at=datetime.utcnow(),
    updated_at=datetime.utcnow()
)
session.add(new_task)
await session.commit()
await session.refresh(new_task)
```

**Edge Cases & Validations**:
- Invalid user_id: Return error indicating user not found
- Missing title: Return error indicating title is required
- Title too long (>255 chars): Return error indicating title exceeds maximum length
- Database connection failure: Return error indicating service unavailable
- Duplicate task creation: Allow (different tasks can have same title)

**Dependencies**:
- SQLModel Task model from previous database foundation
- Database session management from previous implementation
- User validation system (assumed to be handled by caller)

### Tool 2: list_tasks

**Purpose**: Retrieve all tasks for the authenticated user with optional filtering by status.

**Input Parameters**:
- `user_id` (string, required): The ID of the user whose tasks to retrieve
  - Type: string
  - Required: Yes
  - Validation: Must be a valid user ID that exists in the system
  - Format: Alphanumeric string with possible special characters
- `status` (string, optional): Filter tasks by completion status
  - Type: string
  - Required: No
  - Validation: If provided, must be one of "all", "pending", "completed" (case-insensitive)
  - Format: Enum values "all", "pending", "completed"
  - Default: "all" if not provided

**Output Format**:
```json
[
  {
    "id": "string",
    "title": "string",
    "completed": false,
    "priority": "string",
    "due_date": "string",
    "category": "string",
    "created_at": "string",
    "updated_at": "string",
    "completed_at": "string"
  }
]
```

**Behavior / Logic**:
1. Validate input parameters: user_id exists and is valid, status is valid if provided
2. Build query to select tasks filtered by user_id
3. Apply additional filter based on status parameter if provided:
   - "pending": filter where completed=False
   - "completed": filter where completed=True
   - "all" or not provided: no additional filter
4. Execute query and retrieve matching tasks
5. Format results as array of task objects with all required fields
6. Return array of task objects

**SQLModel Syntax Example**:
```python
# Pseudo-code for SQLModel operations
query = select(Task).where(Task.user_id == user_id)
if status == "pending":
    query = query.where(Task.completed == False)
elif status == "completed":
    query = query.where(Task.completed == True)
result = await session.exec(query)
tasks = result.all()
```

**Edge Cases & Validations**:
- Invalid user_id: Return empty array (no tasks found for user)
- Invalid status value: Return error indicating invalid status parameter
- No tasks found: Return empty array
- Database connection failure: Return error indicating service unavailable

**Dependencies**:
- SQLModel Task model from previous database foundation
- Database session management from previous implementation

### Tool 3: complete_task

**Purpose**: Mark a specific task as completed for the authenticated user.

**Input Parameters**:
- `user_id` (string, required): The ID of the user attempting to complete the task
  - Type: string
  - Required: Yes
  - Validation: Must be a valid user ID that exists in the system
  - Format: Alphanumeric string with possible special characters
- `task_id` (string, required): The ID of the task to mark as completed
  - Type: string
  - Required: Yes
  - Validation: Must be a valid task ID that exists in the database and belongs to the user
  - Format: UUID string format

**Output Format**:
```json
{
  "task_id": "string",
  "status": "completed",
  "title": "string"
}
```

**Behavior / Logic**:
1. Validate input parameters: user_id exists, task_id exists and is valid format
2. Verify that the task with task_id belongs to the user with user_id
3. Update the task's completed field to true
4. Set the completed_at timestamp to current time
5. Update the updated_at timestamp to current time
6. Save changes to database
7. Return success response with task ID, status, and title

**SQLModel Syntax Example**:
```python
# Pseudo-code for SQLModel operations
query = select(Task).where(Task.id == task_id, Task.user_id == user_id)
result = await session.exec(query)
task = result.first()

if not task:
    # Return error: task not found or doesn't belong to user
    pass

task.completed = True
task.completed_at = datetime.utcnow()
task.updated_at = datetime.utcnow()

await session.add(task)
await session.commit()
await session.refresh(task)
```

**Edge Cases & Validations**:
- Task not found: Return error indicating task does not exist or doesn't belong to user
- Task already completed: Still mark as completed, return success
- Invalid user_id: Return error indicating unauthorized access
- Invalid task_id format: Return error indicating invalid task ID
- Database connection failure: Return error indicating service unavailable

**Dependencies**:
- SQLModel Task model from previous database foundation
- Database session management from previous implementation

### Tool 5: update_task

**Purpose**: Modify properties of an existing task for the authenticated user.

**Input Parameters**:
- `user_id` (string, required): The ID of the user attempting to update the task
  - Type: string
  - Required: Yes
  - Validation: Must be a valid user ID that exists in the system
  - Format: Alphanumeric string with possible special characters
- `task_id` (string, required): The ID of the task to update
  - Type: string
  - Required: Yes
  - Validation: Must be a valid task ID that exists in the database and belongs to the user
  - Format: UUID string format
- `title` (string, optional): New title for the task
  - Type: string
  - Required: No
  - Validation: If provided, must be between 1-255 characters, not empty or whitespace only
  - Format: Text string
- `description` (string, optional): New description for the task
  - Type: string
  - Required: No
  - Validation: If provided, must be between 1-1000 characters
  - Format: Text string, can be null/empty
- `completed` (boolean, optional): New completion status for the task
  - Type: boolean
  - Required: No
  - Validation: Must be true or false
  - Format: Boolean value

**Output Format**:
```json
{
  "task_id": "string",
  "status": "updated",
  "title": "string"
}
```

**Behavior / Logic**:
1. Validate input parameters: user_id exists, task_id exists and is valid format
2. Verify that the task with task_id belongs to the user with user_id
3. For each provided optional parameter, update the corresponding field in the task
4. If completed status is changing to true and completed_at is not set, set it to current time
5. If completed status is changing to false, set completed_at to null
6. Update the updated_at timestamp to current time
7. Save changes to database
8. Return success response with task ID, status, and updated title

**SQLModel Syntax Example**:
```python
# Pseudo-code for SQLModel operations
query = select(Task).where(Task.id == task_id, Task.user_id == user_id)
result = await session.exec(query)
task = result.first()

if not task:
    # Return error: task not found or doesn't belong to user
    pass

# Update fields if provided in input
if title is not None:
    task.title = title
if description is not None:
    task.description = description
if completed is not None:
    task.completed = completed
    if completed and task.completed_at is None:
        task.completed_at = datetime.utcnow()
    elif not completed:
        task.completed_at = None

task.updated_at = datetime.utcnow()

await session.add(task)
await session.commit()
await session.refresh(task)
```

**Edge Cases & Validations**:
- Task not found: Return error indicating task does not exist or doesn't belong to user
- Invalid user_id: Return error indicating unauthorized access
- Invalid task_id format: Return error indicating invalid task ID
- Invalid field values: Return appropriate validation errors
- Database connection failure: Return error indicating service unavailable
- Attempting to update non-existent fields: Ignore silently

**Dependencies**:
- SQLModel Task model from previous database foundation
- Database session management from previous implementation

## 3. Integration Notes for Next Steps

### MCP SDK Wrapping
The five tools will be wrapped using the Official MCP SDK to create a standardized interface that AI agents can consume. Each function will be registered as an MCP tool with proper metadata, input/output schemas, and error handling. The MCP SDK will handle serialization, deserialization, and transport protocols.

### OpenAI Agents SDK Integration
The MCP tools will be accessible to the OpenAI Agents SDK through the MCP server. The agent will be able to call these tools by name and receive structured responses. The agent's instructions will guide it on when to use each tool based on user requests (e.g., "add task" → add_task tool).

### Statelessness Guarantee
All tools are designed to be stateless - they receive all necessary information as input parameters and persist all state changes to the database. No in-memory state is maintained between tool calls, ensuring scalability and reliability. Each tool call is independent and can be executed on any server instance.
