# Todo AI Chatbot - MCP Server Specification (Step 3)

## 1. Constitution Reinforcement

**Core Isolation Principles:**
- **Complete Isolation**: Phase III must remain completely isolated from Phase II - no modifications to Phase II code, files, or structures
- **READ-ONLY Phase II**: Phase II frontend & backend folders are strictly read-only - no modifications, overwrites, refactors, or direct imports allowed
- **Separation of Concerns**: Phase III operates in separate top-level folders within the same monorepo
- **No Manual Coding**: All code must be generated by Claude Code based on specs, plans, and tasks

**Step 3-Specific Rules:**
- **MCP Server Implementation**: The server MUST expose exactly 5 tools (add_task, list_tasks, complete_task, delete_task, update_task) as specified in Step 2
- **Integration**: MCP tools from Step 2 must be properly integrated into the server via decorators/functions
- **Transport Protocol**: Server MUST support streamable-http transport for OpenAI Agents SDK integration
- **Authentication**: Server MUST validate user_id for each tool call to ensure proper scoping
- **Error Handling**: Server MUST propagate errors from tools in standardized format
- **Statelessness**: Server maintains no internal state between requests - all state in database

## 2. MCP Server Specification

### Server Configuration
- **Name**: "todo-ai-chatbot-mcp-server"
- **Version**: "1.0.0"
- **Instructions**: "MCP server for Todo AI Chatbot that provides tools for managing tasks"
- **Transport**: "streamable-http" for compatibility with OpenAI Agents SDK
- **Host**: "0.0.0.0" to allow external connections
- **Port**: 8002 (to avoid conflicts with main FastAPI app on 8000)
- **Debug Mode**: True during development, False in production

### Tool Integration Requirements
Each of the 5 MCP tools from Step 2 must be properly registered with the server:

#### Tool 1: add_task
- **Registration**: Use `@server.tool()` decorator on the `add_task` function from Step 2
- **Signature**: `add_task(user_id: str, title: str, description: Optional[str] = None) -> Dict[str, Any]`
- **Input Validation**: Server validates user_id, title, and description before calling tool
- **Output Format**: Returns exactly `{"task_id": "string", "status": "created", "title": "string"}`

#### Tool 2: list_tasks
- **Registration**: Use `@server.tool()` decorator on the `list_tasks` function from Step 2
- **Signature**: `list_tasks(user_id: str, status: Optional[str] = None) -> List[Dict[str, Any]]`
- **Input Validation**: Server validates user_id and status parameter before calling tool
- **Output Format**: Returns array of task objects with all required fields

#### Tool 3: complete_task
- **Registration**: Use `@server.tool()` decorator on the `complete_task` function from Step 2
- **Signature**: `complete_task(user_id: str, task_id: str) -> Dict[str, Any]`
- **Input Validation**: Server validates user_id and task_id before calling tool
- **Output Format**: Returns exactly `{"task_id": "string", "status": "completed", "title": "string"}`

#### Tool 4: delete_task
- **Registration**: Use `@server.tool()` decorator on the `delete_task` function from Step 2
- **Signature**: `delete_task(user_id: str, task_id: str) -> Dict[str, Any]`
- **Input Validation**: Server validates user_id and task_id before calling tool
- **Output Format**: Returns exactly `{"task_id": "string", "status": "deleted", "title": "string"}`

#### Tool 5: update_task
- **Registration**: Use `@server.tool()` decorator on the `update_task` function from Step 2
- **Signature**: `update_task(user_id: str, task_id: str, title: Optional[str] = None, description: Optional[str] = None, completed: Optional[bool] = None) -> Dict[str, Any]`
- **Input Validation**: Server validates user_id, task_id, and optional parameters before calling tool
- **Output Format**: Returns exactly `{"task_id": "string", "status": "updated", "title": "string"}`

### Error Handling Specification
- **Validation Errors**: Return structured error responses with error code and message
- **Authorization Errors**: Return error when user_id doesn't match task ownership
- **Not Found Errors**: Return error when task doesn't exist
- **Database Errors**: Return error for database connection issues
- **Generic Errors**: Return error for unexpected issues

### Security Requirements
- **User Isolation**: Each tool call must validate that user_id has permission to access/modify resources
- **Input Sanitization**: All inputs must be validated before processing
- **Rate Limiting**: Implement basic rate limiting to prevent abuse (optional for initial implementation)

## 3. Integration Notes for Next Steps

### OpenAI Agents SDK Integration
The MCP server will be configured to work with OpenAI Agents SDK through the MCP protocol. The agent will be able to call these tools by name and receive structured responses. The agent's instructions will guide it on when to use each tool based on user requests (e.g., "add task" → add_task tool).

### FastAPI Application Integration
The MCP server will run on a separate port (8002) but will share the same database connection pool and authentication mechanisms as the main application. This ensures data consistency while maintaining separation of concerns.

### Testing Strategy
- Unit tests for each registered tool
- Integration tests for the MCP server
- End-to-end tests connecting the OpenAI Agent to the MCP server
